# Stage 9A.1–9A.2 — Revised CMS Table-Level Schema and Integrity Review

**Status:** Proposed design; not approved for migration  
**Implementation:** Not implemented  
**Migration:** No CMS migration file created or applied  
**Environment:** Documentation only; Preview and Production D1 were not accessed or changed  
**Scope:** Seven additive CMS tables; existing operational and legacy tables remain in place

## 1. Design principles

1. Keep the seven-table CMS model additive. Do not replace `pages`, `site_content`, `page_styles`, `audit_logs`, `admin_users`, or operational tables.
2. English and Bangla are separate editing and publication scopes.
3. Editable structure is the working Draft. Public rendering reads immutable published snapshots only.
4. Page publication is atomic for one page and one language.
5. Global publication is independent for EN and BN (the user's confirmed Option A). It is not bundled into page publication.
6. Defaults are baseline values, not published values. A Default action copies the selected locale's baseline into Draft only.
7. CMS deletes are soft deletes. Historical rows and published snapshots are retained.
8. All actor-sensitive operations are server-authorized. Reuse `audit_logs` for structural/admin events.
9. Keep page styles and business/operational domains outside these seven CMS tables.
10. The definitions below are a logical table-level contract, not executable migration SQL. Actual D1 schema and SQLite feature compatibility remain unverified.

## 2. Proposed table definitions

Conventions:
- Primary identifiers are proposed as `TEXT` IDs generated by the application (UUID or another consistently generated opaque ID).
- Timestamps are proposed as UTC ISO-8601 text values.
- Boolean fields use integer values constrained to `0` or `1`.
- JSON-bearing columns are stored as TEXT. Server-side parsing and schema validation are mandatory. Do not add `json_valid()` CHECK constraints until its availability and behavior are verified against the target D1 SQLite runtime.
- Foreign-key deletion behavior is restrictive. No CMS parent deletion physically cascades into child content or history.

### 2.1 `cms_pages` — logical page registry

| Column | Type | Null/default | Rule / purpose |
|---|---|---|---|
| `id` | TEXT | NOT NULL | Primary key |
| `page_key` | TEXT | NOT NULL | Stable machine key; UNIQUE |
| `page_type` | TEXT | NOT NULL | CHECK: `static`, `system`, `builder`, `global` |
| `is_system` | INTEGER | NOT NULL DEFAULT 0 | CHECK 0/1; system pages cannot be removed through CMS |
| `created_at` | TEXT | NOT NULL | UTC timestamp |
| `updated_at` | TEXT | NOT NULL | UTC timestamp |

Constraints/indexes:
- PRIMARY KEY (`id`); UNIQUE (`page_key`).
- CHECK that `page_type='global'` is represented by the reserved `page_key='global'` is recommended, but the exact registry seed/constraint should be finalized with the page registry.
- No hard-delete API. Registry retirement, if ever needed, requires an explicit lifecycle field and compatibility policy rather than deleting identity.

### 2.2 `cms_page_locales` — language-specific page workspace

| Column | Type | Null/default | Rule / purpose |
|---|---|---|---|
| `id` | TEXT | NOT NULL | Primary key; locale identity |
| `page_id` | TEXT | NOT NULL | FK to `cms_pages.id`, ON DELETE RESTRICT |
| `locale` | TEXT | NOT NULL | CHECK: `en` or `bn` |
| `route_path` | TEXT | NOT NULL | Locale-specific public route; unique after route normalization |
| `title` | TEXT | NOT NULL | Locale-specific title |
| `page_status` | TEXT | NOT NULL DEFAULT 'draft' | CHECK: `draft`, `published`, `archived` |
| `seo_title` | TEXT | NOT NULL DEFAULT '' | Locale-specific SEO title |
| `seo_description` | TEXT | NOT NULL DEFAULT '' | Locale-specific SEO description |
| `legacy_page_id` | TEXT | NULL | Optional link to existing `pages.id`; FK only after actual legacy schema/data verification |
| `draft_revision` | INTEGER | NOT NULL DEFAULT 0 | Monotonic revision incremented by every draft mutation |
| `publication_revision` | INTEGER | NOT NULL DEFAULT 0 | Monotonic successful-publication counter |
| `current_published_version_id` | TEXT | NULL | Pointer to the current published `cms_page_versions` row for this locale |
| `created_at` | TEXT | NOT NULL | UTC timestamp |
| `updated_at` | TEXT | NOT NULL | UTC timestamp |
| `published_at` | TEXT | NULL | Last successful publication time |

Constraints/indexes:
- PRIMARY KEY (`id`); UNIQUE (`page_id`, `locale`).
- FK (`page_id`) REFERENCES `cms_pages(id)` ON DELETE RESTRICT.
- UNIQUE normalized route per locale is required. Whether route uniqueness is global or locale-scoped must be aligned with the Worker routing rules before SQL is finalized.
- `legacy_page_id` must not be constrained until the existing `pages` key and actual D1 state are confirmed.
- The published-version pointer must be constrained to a version belonging to the same locale. The recommended composite relationship is described in Section 4; if SQLite/D1 cannot support the chosen cyclic deferred FK cleanly, enforce same-locale ownership inside the atomic publication service and add a verification query.
- Global has one `cms_pages` row and exactly two locale rows, `en` and `bn`. Seed enforcement is part of migration validation.

### 2.3 `cms_sections` — editable locale-specific section structure

| Column | Type | Null/default | Rule / purpose |
|---|---|---|---|
| `id` | TEXT | NOT NULL | Primary key; preserve legacy section ID where safe |
| `page_locale_id` | TEXT | NOT NULL | FK to `cms_page_locales.id`, ON DELETE RESTRICT |
| `section_key` | TEXT | NOT NULL | Stable key unique within the locale, including deleted rows |
| `section_type` | TEXT | NOT NULL | Renderer type; preserve `hero`, `text`, `split`, `cards`, `cta`; extensible only through a registered renderer |
| `label` | TEXT | NOT NULL DEFAULT '' | Admin-facing label |
| `position` | INTEGER | NOT NULL DEFAULT 0 | Non-negative ordering value |
| `required` | INTEGER | NOT NULL DEFAULT 0 | CHECK 0/1; required sections cannot be deleted |
| `config_json` | TEXT | NOT NULL DEFAULT '{}' | Renderer/layout configuration, validated server-side |
| `is_active` | INTEGER | NOT NULL DEFAULT 1 | Draft structure state only; CHECK 0/1 |
| `deleted_at` | TEXT | NULL | Soft-delete timestamp |
| `created_at` | TEXT | NOT NULL | UTC timestamp |
| `updated_at` | TEXT | NOT NULL | UTC timestamp |

Constraints/indexes:
- PRIMARY KEY (`id`); UNIQUE (`page_locale_id`, `section_key`).
- FK (`page_locale_id`) REFERENCES `cms_page_locales(id)` ON DELETE RESTRICT.
- CHECK `position >= 0`; CHECK booleans are 0/1.
- Index (`page_locale_id`, `is_active`, `position`).
- Do not hard-delete sections. Do not use the editable `is_active` field to decide public visibility; publication snapshots determine public structure.

### 2.4 `cms_content_elements` — editable section elements

| Column | Type | Null/default | Rule / purpose |
|---|---|---|---|
| `id` | TEXT | NOT NULL | Primary key; preserve stable legacy element ID/key where possible |
| `section_id` | TEXT | NOT NULL | FK to `cms_sections.id`, ON DELETE RESTRICT |
| `element_key` | TEXT | NOT NULL | Stable key unique within section, including deleted rows |
| `element_type` | TEXT | NOT NULL | CHECK: `text`, `textarea`, `rich_text`, `url`, `image`, `list`, `option_list`, `seo_text`, `system_text` |
| `label` | TEXT | NOT NULL DEFAULT '' | Admin-facing label |
| `position` | INTEGER | NOT NULL DEFAULT 0 | Non-negative ordering value |
| `required` | INTEGER | NOT NULL DEFAULT 0 | CHECK 0/1; parent section cannot be deleted while required children exist |
| `config_json` | TEXT | NOT NULL DEFAULT '{}' | Editor constraints, validation and renderer metadata |
| `is_active` | INTEGER | NOT NULL DEFAULT 1 | Draft structure state only; CHECK 0/1 |
| `deleted_at` | TEXT | NULL | Soft-delete timestamp |
| `created_at` | TEXT | NOT NULL | UTC timestamp |
| `updated_at` | TEXT | NOT NULL | UTC timestamp |

Constraints/indexes:
- PRIMARY KEY (`id`); UNIQUE (`section_id`, `element_key`).
- FK (`section_id`) REFERENCES `cms_sections(id)` ON DELETE RESTRICT.
- CHECK `position >= 0`; CHECK booleans are 0/1.
- Index (`section_id`, `is_active`, `position`).
- Explicitly retain `textarea`; do not silently map it to `text`.
- An element belongs to a locale through its section; its value/default/history therefore inherits the locale scope.

### 2.5 `cms_content_values` — locale baseline and editable value

| Column | Type | Null/default | Rule / purpose |
|---|---|---|---|
| `element_id` | TEXT | NOT NULL | Primary key and FK to `cms_content_elements.id`, ON DELETE RESTRICT |
| `default_value_json` | TEXT | NOT NULL | Immutable baseline for this element and locale |
| `draft_value_json` | TEXT | NOT NULL | Current editable value; JSON-encoded value preserves strings, arrays and structured data |
| `updated_at` | TEXT | NOT NULL | UTC timestamp |

Constraints/indexes:
- PRIMARY KEY (`element_id`).
- FK (`element_id`) REFERENCES `cms_content_elements(id)` ON DELETE RESTRICT.
- Defaults are immutable through ordinary CMS API/UI actions. A controlled seed/schema upgrade may revise a baseline with an audited migration.
- The Default action copies `default_value_json` to `draft_value_json` for the selected element and locale only, increments the owning locale's `draft_revision`, and does not alter any published snapshot.
- No separate mutable published value is stored here. Published values live in immutable page-version snapshots.

### 2.6 `cms_content_versions` — element-level value history

| Column | Type | Null/default | Rule / purpose |
|---|---|---|---|
| `id` | TEXT | NOT NULL | Primary key |
| `element_id` | TEXT | NOT NULL | FK to `cms_content_elements.id`, ON DELETE RESTRICT |
| `version_no` | INTEGER | NOT NULL | Monotonic per element |
| `value_json` | TEXT | NOT NULL | Immutable historical value |
| `change_reason` | TEXT | NOT NULL DEFAULT '' | Optional short reason |
| `actor_email` | TEXT | NOT NULL | Email snapshot for readable attribution |
| `created_at` | TEXT | NOT NULL | UTC timestamp |

Constraints/indexes:
- PRIMARY KEY (`id`); UNIQUE (`element_id`, `version_no`).
- FK (`element_id`) REFERENCES `cms_content_elements(id)` ON DELETE RESTRICT.
- Index (`element_id`, `version_no` DESC).
- This table is recovery history, not a replacement for `audit_logs`. Structural actions and publish/restore/permission events remain in the existing audit log.

### 2.7 `cms_page_versions` — immutable published snapshots

| Column | Type | Null/default | Rule / purpose |
|---|---|---|---|
| `id` | TEXT | NOT NULL | Primary key |
| `page_locale_id` | TEXT | NOT NULL | FK to `cms_page_locales.id`, ON DELETE RESTRICT |
| `version_no` | INTEGER | NOT NULL | Monotonic per page locale |
| `source_draft_revision` | INTEGER | NOT NULL | Draft revision captured by this publication |
| `snapshot_json` | TEXT | NOT NULL | Complete self-contained published snapshot |
| `actor_email` | TEXT | NOT NULL | Publisher email snapshot |
| `published_at` | TEXT | NOT NULL | UTC publication timestamp |

Constraints/indexes:
- PRIMARY KEY (`id`); UNIQUE (`page_locale_id`, `version_no`); UNIQUE (`id`, `page_locale_id`).
- FK (`page_locale_id`) REFERENCES `cms_page_locales(id)` ON DELETE RESTRICT.
- Index (`page_locale_id`, `version_no` DESC).
- Snapshot is immutable after insertion. A correction creates a new publication version; it never edits a prior snapshot.
- Snapshot includes all rendering dependencies for that locale/version: page key/type, route, locale, title, SEO metadata, ordered active sections, section type/config, ordered active elements, element type/config and values, plus any safe renderer metadata needed to reproduce that publication.
- Snapshot records the exact structure/value set at publication time. It must not require reads from mutable draft rows to render the page.

## 3. Relationships

```text
cms_pages 1 ─── N cms_page_locales
                    │
                    ├── 1 ─── N cms_sections
                    │             │
                    │             └── 1 ─── N cms_content_elements
                    │                           │
                    │                           ├── 1 ─── 1 cms_content_values
                    │                           └── 1 ─── N cms_content_versions
                    │
                    └── 1 ─── N cms_page_versions
                           ▲
                           └── current_published_version_id (nullable pointer)

Existing audit_logs records structural, publication, restore and administrative events.
Existing pages may be linked through legacy_page_id after verification.
Existing site_content keys are mapped into CMS values during reviewed backfill.
page_styles stays separate.
```

## 4. Integrity and transaction review (Stage 9A.2)

### 4.1 Same-locale published-version pointer

A simple FK from `current_published_version_id` to `cms_page_versions.id` prevents a dangling pointer but does not prevent pointing to a version belonging to another locale.

Preferred relational constraint:
- Keep `UNIQUE(id, page_locale_id)` on `cms_page_versions`.
- Use a composite FK from `cms_page_locales(current_published_version_id, id)` to `cms_page_versions(id, page_locale_id)`.
- The pointer is NULL before first publication.
- Insert the version and update the locale pointer in one atomic transaction.
- Because the tables refer to each other, verify D1/SQLite deferred-FK behavior with a Preview-only compatibility test before choosing this exact DDL. If unsupported or operationally awkward, retain a simple FK and enforce same-locale ownership inside the transaction plus a periodic integrity query.

### 4.2 Atomic page publication and optimistic concurrency

The publication service must:
1. Require the selected locale's expected `draft_revision` and expected `publication_revision`.
2. Read and validate the current editable tree and all values for that locale.
3. Build a complete immutable snapshot from active Draft sections/elements only.
4. Insert the next `cms_page_versions` row with the captured `source_draft_revision`.
5. Advance `current_published_version_id`, increment `publication_revision`, set `published_at` and update `page_status` only if both expected revisions still match.
6. Commit all operations atomically. If the conditional update affects no row, roll back and return a version-conflict response. A failed operation must leave the prior published pointer and snapshot unchanged.

Use D1's supported transactional/batch mechanism only after verifying its semantics for the chosen statements. Do not assume separate Worker requests form one transaction.

### 4.3 Draft mutation rules

- Every structural or value mutation increments the owning `cms_page_locales.draft_revision` in the same transaction as the mutation.
- Save Draft never changes `current_published_version_id` or `publication_revision`.
- Default copies the immutable baseline to Draft only.
- Restore from history copies the selected historical content into current Draft, increments `draft_revision`, and leaves publication unchanged.
- A stale editor must receive a conflict response rather than silently overwrite newer Draft data.

### 4.4 Soft-delete and restore

- Required sections and required elements cannot be deleted.
- An optional section containing any required element cannot be deleted.
- Soft-deleting a section sets its own Draft deletion state only; it does not physically delete descendants or history.
- An individually deleted child remains deleted if its parent section is later restored. Parent restore must not bulk-reactivate descendants.
- Restore changes editable Draft structure only. It does not alter the current public snapshot.
- At the next successful page/language publication, the snapshot builder excludes deleted sections and all descendants, as well as individually deleted elements.
- Stable keys remain reserved by soft-deleted rows. Re-creation must use an explicit restore or a new key.

### 4.5 Global scope integrity — confirmed Option A

- One `cms_pages` registry record uses `page_type='global'`; exactly one EN and one BN locale workspace are seeded.
- Global EN and BN maintain separate Draft revisions, publication revisions, current-version pointers and version histories.
- Global publish advances only the selected Global locale.
- Ordinary page publish advances only the selected ordinary page locale.
- Public rendering composes the selected page's published snapshot with the current published Global snapshot for the same locale. Global Draft is never read by public routes and is never embedded in ordinary page snapshots.
- Global history restore changes Draft only.
- Successful Global publication invalidates/revalidates cached responses for the matching language. The exact mechanism must be checked against the actual Worker and Cloudflare cache path before implementation.
- Define a safe pre-first-publication Global baseline/fallback before rollout; do not fall back to draft data.

### 4.6 Audit attribution

Reuse existing `audit_logs` for page/section/element creation, edit, reorder, delete, restore, Default, publish, history restore, route change and permission-sensitive actions. Keep the existing email snapshot. A stable `admin_user_id` column is a possible additive enhancement, but do not add it until the exact `admin_users` key and existing audit schema are rechecked. No new generic audit table is proposed.

### 4.7 Legacy and operational boundaries

- `pages`: preserve IDs, slugs, locale, title, SEO fields and JSON content; link with `legacy_page_id` only after actual schema and duplicate-route checks.
- `site_content`: map every key with an explicit source/target/type rule. Preserve `text`, `textarea` and `url` semantics and values. Existing immediate-publish behavior must not leak into the CMS Draft workflow.
- `page_styles`: remains a separate draft/published style domain.
- Courses, discounts, syllabus files, learners, registrations, inquiries, quotations, chat, analytics and media assets remain in their existing operational tables/services; do not duplicate them in CMS.
- Route uniqueness and redirects must be designed against the current Worker routing behavior. Do not change public routes as part of an unreviewed backfill.

## 5. Index plan

Required indexes, subject to query-plan validation:
- `cms_page_locales(page_id, locale)` — unique constraint already supplies lookup support.
- `cms_sections(page_locale_id, is_active, position)`.
- `cms_content_elements(section_id, is_active, position)`.
- `cms_content_versions(element_id, version_no DESC)`.
- `cms_page_versions(page_locale_id, version_no DESC)`.
- Unique route index using the exact normalized route expression/column selected after route behavior review.
Avoid redundant indexes that duplicate UNIQUE constraints.

## 6. Stage 9A.2 integrity findings and remaining decisions

| ID | Finding | Design disposition |
|---|---|---|
| I-01 | A published-version ID alone does not guarantee the version belongs to the same locale | Composite same-locale FK preferred; verify deferred cyclic FK support, otherwise enforce transactionally |
| I-02 | Draft edits and published reads must not share mutable structure | Immutable complete page snapshots are the public source of truth |
| I-03 | Two concurrent editors/publishers can overwrite each other without revision checks | Draft and publication revisions plus conditional atomic update |
| I-04 | Parent soft-delete can accidentally reactivate deleted children | Parent and child states remain independent; restore never bulk-reactivates descendants |
| I-05 | Existing audit table may not identify a stable admin account | Reuse existing audit log; inspect exact schema before deciding on additive actor ID |
| I-06 | Route uniqueness rules depend on actual Worker routing | Pending source-level route audit before executable SQL |
| I-07 | Global fallback before first publication and cache invalidation are delivery concerns | Must be specified and tested before rollout |
| I-08 | JSON CHECK functions and cyclic FK behavior are runtime-dependent | Verify against Preview D1; do not assume compatibility |
| I-09 | Existing legacy rows and IDs are not yet confirmed in Preview | Read-only Preview D1 inspection and source mapping remain mandatory |
